# Update the plugin through a detached script and a state file

The Updates page pulls new commits of `origin/main` into the plugin folder. The shell's plugin watcher answers any write in that folder with a global reload about 150 ms later, and the reload destroys the service, every panel and every `Process` they own, sometimes in two bursts. Nothing that starts the update from inside the plugin survives to report its result, and the host gives a plugin no reload hook, no path and no update helper.

That reload does not load new code. It recreates the plugin from the components the shell already compiled, since `shell.qml` clears the component cache only when `Qt.clearComponentCache` is a function, and on quickshell 0.3.1 it is not. Both the QML files and the `.pragma library` JS stay as they were. We measured it twice. An offscreen `qs` script that changed a QML file and a `.pragma library` file, then recreated the component from the same URL, printed `qml=old js=old`. On the real shell, switching the installed clone to a branch with a new migration reloaded the plugin without running the migration, and only `omarchy-restart-shell` ran it.

`data/update.sh` does all of the git work and has three modes. `status` prints the checkout as `key value` lines and touches nothing. `check` fetches `origin/main` and records what is new. `apply` fetches, refuses anything that could lose work, extracts `origin/main` into a temporary folder beside the state file, outside the plugin folder, runs `omarchy-plugin-validate` there when it is installed and then the smoke of `omanotes-db` (ADR-0018), and only then fast-forwards `main` to the commit it validated. It records `updated` with the step `restart`, restarts the shell with `omarchy-restart-shell`, records the update again with the restart's result, and then sends a notification. The watcher still reloads the plugin after the merge, with the old code, and the restart then replaces the shell with one that loads the new code. Both write the state file `${XDG_STATE_HOME:-~/.local/state}/omanotes/update`, whole, through a temporary file and a move. `data/Updater.qml` starts `apply` in its own `systemd-run --user` unit, outside the shell's process tree, and reads the state file, so the panel that comes back after the restart shows the result. The service owns the Updater that checks daily, and every panel uses it once the widget hands the panel the service. Until then a panel makes its own Updater, which runs `status` and never checks by itself: in a shell without the service for as long as the panel lives, and with the service for the moment between the panel's creation and the handoff. `data/Update.js` turns the status lines and the state file into the one view the page draws.

## Considered options

- `omarchy plugin update othavi0.omanotes --yes`. It fetches `origin HEAD` rather than `main`, finds local changes only when the merge fails, leaves its result on stderr only, and a `Process` running it dies with the reload.
- A lock file or a result file inside the plugin folder. Any write there that is not under `.git` reloads the shell.
- Leaving the new code to the watcher's reload. It keeps the compiled components, as measured above, so the plugin would run the old code until the next restart or login, and a new migration would not run.

## Consequences

- Apply refuses before it touches the tree, and records why: local changes (`dirty`), a branch other than `main` (`offMain`), local commits that `origin/main` lacks (`diverged`), an untracked path the merge would refuse to overwrite (`untracked`, with the first such path as the detail): one `origin/main` tracks, one where it tracks a folder, or one inside a path it tracks as a file, a folder that is not the top of its own work tree (`notGit`, so an update never pulls a parent repository) and no `origin` (`noOrigin`). A fetch that fails is `offline`. Files git ignores are left out: the merge overwrites an ignored file that `origin/main` starts to track, as git does.
- A version that does not validate is recorded as `invalid` and never reaches the plugin folder: nothing there is written, so the shell does not reload and there is nothing to roll back. The host's own updater merges first and resets on a failed validation; a reset that fails, for instance on a lock another git holds, leaves a folder that the shell loads anyway.
- The smoke runs the copy's `bin/omanotes-db.<machine>` on this machine, whether or not `omarchy-plugin-validate` is installed. The file is a regular file with the executable bit, the `e_machine` field of its ELF header names the machine `uname -m` reports, and `timeout 20 env -i <binary> <PROTOCOL> selftest <folder>` exits 0, with `PROTOCOL` read from the copy's `data/Db.js`. The header is read because a start proves nothing: with qemu's binfmt, which the development machine has, an aarch64 binary starts on x86_64 and exits 255. The selftest migrates a new database on disk, writes to it and reads it back, so a glibc or `libsqlite3` the binary cannot use, a file system mounted noexec, or a protocol the copy's QML does not speak fails before the merge (on a noexec mount the executable check itself fails, since the kernel answers `access(X_OK)` with the mount flag; measured with `unshare` on a noexec tmpfs). Each failure is `invalid`, with a detail such as `bin/omanotes-db.x86_64 is not executable (no x bit, or a noexec mount)` or `omanotes-db does not speak protocol 2 of data/Db.js`.
- The copy lives in a `validate.XXXXXX` folder beside the state file, not in `/tmp`. `/tmp` is often mounted noexec, and the smoke would then refuse every binary, even one that runs from the plugin folder. An apply removes the copies a SIGKILL left behind before it makes its own, since it holds the lock.
- Known limit: an apply runs the `update.sh` already installed, not the one it pulls. The first update that brings `omanotes-db` still runs the script from before the smoke, so that one update can merge a binary that does not run here. The panel's reads then fail as `no_binary` or `crash` (ADR-0018) until the user pulls a version whose binary runs, through the Updates page or by hand (inferred: the Updater does not use the binary; not tested on a machine where the binary fails).
- A merge that git refuses after all is `mergeFailed`, with git's first error line. `diverged` means only local commits.
- The script exports `GIT_OPTIONAL_LOCKS=0`, so `status`, which several panels run at any moment, never takes `index.lock` from under the merge. `test/update.sh` runs eight applies against four `status` loops.
- The state file keeps whole hashes, so two runs never compare abbreviations of different lengths. The page shortens them.
- ssh runs with `-oBatchMode=yes` on top of the user's ssh command, since the unit has no terminal to answer a prompt.
- The script exits 0 once it recorded a result, a refusal or a failed restart included, 3 when the lock stayed taken for a minute and 1 when it could record nothing, or pulled but could not record the update.
- The restart runs only after a pull that landed, never on a refusal, an `invalid` or a `mergeFailed`. The unit runs outside the shell, so it survives the restart. `omarchy-restart-shell` finds the session's `OMARCHY_PATH` through `systemctl --user show-environment`, derives `HYPRLAND_INSTANCE_SIGNATURE` when it is missing, and exits 1 when the session is locked or the new shell does not answer its ping.
- A restart that fails keeps the phase `updated` and records `error restartFailed` with the first line the command wrote to stderr as the detail. A missing `omarchy-restart-shell` is recorded the same way. The Updates page then says the shell did not restart and asks the user to run `omarchy restart shell`. The next check that finds nothing new keeps the `updated` record but drops the error.
- An `updated` record whose step is still `restart` reads as updating, at the restart step, for five minutes, and after that as a failed restart. The page shows four steps while updating: fetch, validate, pull and restart.
- The notification goes out after the restart returns, because a notification shown by the old shell dies with it. When the restart failed, it also asks the user to run `omarchy restart shell`.
- The copy being validated is removed on any exit of the script, including the SIGTERM systemd stops the unit with when it outlives `RuntimeMaxSec`.
- The script is `main "$@"; exit $?` on one line, so bash has read all of it before the merge replaces it. `test/update.sh` proves an update that rewrites the script itself.
- `flock` on `update.lock` beside the state file serializes the service's daily check, a click in any panel and an apply. Each waits up to a minute for it. Every command the script starts runs with the lock's descriptor closed, so a `git gc` that git detaches never keeps the lock.
- A check that cannot reach origin records `offline` and keeps what the last fetch put in `origin/main`. A check that finds nothing new after an update keeps the `updated` record, so the result of an update is not replaced by the check queued behind it.
- A check result counts only against the HEAD it was made on, so any later pull, ours or the host's, clears the dot. An `updating` record older than five minutes reads as stopped.
- The service's Updater is the only one that checks by itself, once a day, when Check daily is on, so several monitors never mean several fetches. It looks on the minute and checks when the day, or the hour after an `offline` record, has passed since the record. A check that ends without a record, such as one that could not write the state file, waits an hour before the next, since no record says it ran. Without a service a manual check still works. A test drives the service's clock and never fetches.
- `systemd-run` runs through a `Process` without `--wait`, so it returns once the unit is queued. A launcher that exits non-zero shows "Could not start the update" with its first stderr line in the panel that asked. From the click until the first record of that apply, the page shows the update as started and offers no Update. `apply` takes the unit's name as its request and writes it in every record, and only a record with that request ends the wait, so a check's record written in the same second does not. A record that has not appeared after 90 s, longer than apply waits for the lock, reads as "The update did not start." A check that ends without a record says why the same way.
- The unit gets `PATH`, `XDG_STATE_HOME`, `OMARCHY_PATH`, `DBUS_SESSION_BUS_ADDRESS`, `WAYLAND_DISPLAY`, `SSH_AUTH_SOCK` and `HYPRLAND_INSTANCE_SIGNATURE` from the shell when they are set: the user manager may lack them, and the validator, the restart, the notification and an ssh fetch need them. With the shell's own `HYPRLAND_INSTANCE_SIGNATURE`, the restart talks to the Hyprland that runs this shell rather than the newest instance it finds.
- Update is off while an alarm rings, because the reload and the restart would drop the ring. The service binds its Updater's `blocked` to the ring, and `apply()` itself refuses while it is set, whoever calls it.
- The panel closes with the reload, so the notification is what the user sees at once. The Updates page shows the result when the panel opens again.
- `test/update.sh` publishes this machine's committed binary and the real `data/Db.js`, so every apply in it passes through the smoke. Then it publishes one broken version per failure: no binary, a symlink, no executable bit, the other machine's build, a binary that fails its selftest (a copy of `false`), a `PROTOCOL` the binary refuses, and a broken binary with no `omarchy-plugin-validate`. Each ends `invalid` with its detail and writes nothing in the plugin folder. Each check failed with the smoke removed, and the machine check also failed with only the ELF check removed. `test/behavior.sh` and `test/alarm.sh` put the binary and `data/Db.js` in their origin too.
- `test/update.sh` puts an `omarchy-restart-shell` stub first in `PATH` and stops before any apply when it is not the one found. The run without the command uses a `PATH` of links to the tools the script needs, because the real command restarts the shell of the session running the tests. `test/behavior.sh` and `test/alarm.sh`, which run a real apply, stub it too.

# Alarms ring from one plugin service

Omanotes runs one bar widget per monitor, and each widget has its own `Db` (ADR-0004). An alarm needs things that must exist once per shell: the clock that finds a due alarm, the ring card and the sound, the notification for missed alarms, and the write that marks an occurrence as rung. The plugin therefore declares a service next to the bar widget (`manifest.json`, `kinds: ["service", "bar-widget"]`). The shell creates `Service.qml` once, whatever the number of bars, and each `BarWidget` finds it through `bar.shell.serviceFor(moduleName)` and hands it to its panel. The service owns a `SystemClock`, the ring state, the player `Process`, the notification call, one ring window per screen while ringing, and the only `Data.AlarmsDb`, the store of the `alarms` table. The widgets and the Alarms tab read its properties and call its functions. Nothing else in the shell writes the `alarms` table.

The alarm maths is pure (`data/Alarm.js`, ported from Chime) and every alarm string is pure (`ui/Alarms.js`), so Node tests both (ADR-0009). Instants are epoch ms, unlike the seconds of items.

## Considered options

- A leader widget, the first of `bar.moduleWidgets(moduleName)`, owning the clock. Unplugging the leader's monitor loses or doubles the ring during the handoff, and nothing rings while the widget is off the bar.
- A QML singleton for the clock. It lives outside the shell's plugin lifecycle: it keeps ringing after the plugin is disabled and never picks up new code on reload.
- Reading alarms through the widget Dbs, with the tab writing through its own widget's Db. That gives the table N writers with caches up to 80 ms stale, and a tick patch built from one cache can undo a switch flipped through another.

## Consequences

- One writer. A tick, a snooze, an expiry and every edit in the Alarms tab go through the service into its own `Db`. A stop writes nothing: it only drops the ring state. A write sends the whole record (`alarm.save` with the 11 columns of the protocol, from `Db.alarmCells`), so sending it twice leaves the same row, and a failed write is retried with back-off from 500 ms to 30 s without harm. A write refused for what it is, by the schema, the side, the request or its size, is not retried: it would be refused again (`Db.definitive`, ADR-0018).
- The service lays each write over its cached row before the write is queued (`data/AlarmsDb.qml`, `_pending`). The next tick sees the patched record whether the write is queued, waiting on a lock or being retried, so an occurrence never rings twice. A snapshot drops a pending entry only when it was read after that write ended (`Store.covered`), so a read that ran before the write cannot bring the old row back. This is the one exception to the file being the single source of truth (ADR-0004), and it covers only rows the service wrote itself. `Db.parseAlarms` rounds every number of a row into the range `Db.alarmCells` accepts, so a hand edit that stored a fraction or a negative instant is still written back, and a record that cannot be sent anyway stays laid over its row, so a tick consumes an occurrence once.
- `data/AlarmsDb.qml` and the widgets' `data/ItemsDb.qml` are both views over `data/Store.qml`, which holds the write queue, the watcher and the snapshot (ADR-0018). The binary refuses an alarm write that does not come from the service. Neither view carries the other's writes or signals.
- Alarm time comes from `tick(nowMs)`, never from `Date.now()`. Only the player latch, which counts how fast a player process failed, reads the wall clock. Production calls `tick` from the `SystemClock` once a second. Tests set `clockRunning: false` and call it with the instants they want, so the ring, the grace window, the snooze and the three automatic snoozes are proven offscreen (`test/alarm.sh`). Inside a change handler a binding that depends on the changed property still holds its old value, so the service drops a ringing alarm taken away outside on `AlarmsDb.shown`, which fires once `alarms` and `alarmsById` both hold the new list.
- The ring window is an injected `Component`, one instance per screen while ringing. The shipped one, `ui/RingWindow.qml`, is a layer-shell `PanelWindow` on the Overlay layer with no keyboard focus, no exclusion zone and a mask over the card, like the shell's notification popups. It has no offscreen backend, so the service compiles it from its URL only when nothing was injected, and a test passes a plain window around the real `ui/RingCard.qml`.
- The card takes no keyboard focus and handles no key (ADR-0013). Chime's Esc, Enter, Space and S are not ported. A ring is stopped with the mouse, on the card or on the bar chip.
- The ring state lives in memory only. A plugin reload or a shell restart drops a ring in progress. `last_fired_at_ms` is already on disk by then, so the alarm does not ring again.
- Without a service, in an older shell or in `test/panel.sh`, the widget and the panel still work: the chip shows the note glyph alone and the Alarms tab shows an empty state. The Settings pages still save, since the settings live in the widget's `Db` (ADR-0016), and only the buttons that play a sound say they need the service.
- The ring's sound, volume and Sound switch come from the settings row, which the service reads and never writes. A custom file that is gone plays the default sound, and a volume goes to each player as a whole number under `LC_ALL=C`. Settings tests a sound through `togglePreview`, a second player that a ring stops and that never touches the ring's latch. `previewEnded` carries the page that asked, so a sound that cannot play is reported in that panel only, by the name of the sound it tested.
- A ring starts one process for its sound, and the repeat lives in it: a bash loop that plays the sound, waits 350 ms and plays it again, until the service stops it. pw-play and paplay cannot loop a file, so each repeat still starts the player itself, but no longer a new process from the shell with a new bash. Before, the loop was a QML `Timer` that started a new `Process` after each play, about 667 of them for a 5 min ring of Bell. The gap is a `read -t` on the stdin pipe the service holds open, which reaches end of file when the shell is gone, so the loop ends by itself after a crash, once the play in progress ends. Stop, Snooze and the Sound switch send TERM, and a trap stops the player. When the shell quits it kills the loop with SIGKILL and no trap runs, so each player runs under `setpriv --pdeathsig TERM` and dies with the loop. A player that fails ends the loop with its exit code, and the latch counts the loop as it counted the player. The loop reads the file and the volume when the ring starts, so a sound or a volume changed during a ring reaches the next ring. A preview plays once, with no loop. `test/alarm.sh` counts the processes a ring starts, the gap between plays and the players left after Snooze, Stop and the shell's exit.
- The alarm editor commits on leave like the item editor (ADR-0007). A draft nobody touched is dropped, a draft with no readable time stays open with a warning, and an add the service refuses (the limit, which counts inserts still in flight, or a service not loaded yet) or an insert that fails keeps or gives back the draft.
- Each tab passes itself as the caller of its writes, and the service's `alarmAdded` and `writeFailed` carry it back, so only the tab that asked selects the new alarm, shows the error or gets the draft back. A write without a caller (a tick, a snooze, a retry) only logs.
- `test/alarm.sh` proves the service with stubs for the player, the notification and the database binary, including a read held across a tick, a save that fails until its retry lands, and an insert that fails and gives the draft back. The limits are in `data/Alarm.js`: 50 alarms, a label of 40 characters, a snooze of 1 to 180 minutes (9 by default) and a ring of 1 to 60 minutes (5 by default).

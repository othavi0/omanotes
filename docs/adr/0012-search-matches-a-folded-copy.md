# Search matches a folded copy of title and body

SQLite's `LIKE` and `lower()` only fold ASCII, so a search for `CAFÉ` missed `Café`, and SQLite has no ICU to fold the rest. Each item keeps a folded copy of its title and body in `search_title` and `search_body`, and the binary folds the query the same way before matching the copy with `LIKE` (ADR-0018). The fold is lower case, then the accents of the Combining Diacritical Marks block (U+0300 to U+036F) dropped through NFD, one UTF-16 unit at a time. `db/Schema/search_map.tsv` holds it as data: every unit the fold changes (2299 rows, sha256 `406fc008…`), and `db/Fold.cs` applies that table. `item.add` and `item.update` write the copy with the item.

## Consequences

- Items inserted or edited with `sqlite3`, outside Omanotes, do not write the copy. Two triggers fold it in SQL for them: `items_search_insert` when an insert leaves `search_title` NULL, and `items_search_update` when an update sets the title or body and leaves both copies as they were. A write that sets a copy itself is kept as it is. An Omanotes edit that keeps both copies the same, such as a change of case only, is folded again by the trigger, with the same result.
- The SQL fold goes through the table `search_map`, filled from the same TSV, one character at a time. The migration that adds the columns creates the map and the triggers, and folds the items already there. Folding one unit at a time is what lets the SQL match the binary on every item; folding whole strings can differ, as Node's `toLowerCase` does on a final Greek sigma.
- Characters outside the Basic Multilingual Plane are not folded, in the binary or in SQL.
- The binary never calls .NET's case or normalization code (`db/BannedSymbols.txt`), so a runtime update cannot fold new rows differently from the rows already stored. A change to the fold is a new migration and a new table.
- The table was generated once from the `searchText` of the JS that folded before the binary, and it equals the `search_map` of the live database. `test/bin-schema.test.mjs` holds the TSV to that function (kept in `test/lib/legacy-db.js`) and to the sha256, and `test/bin-parity.test.mjs` holds the binary's fold to the triggers'.
- Filling 1000 items of 1000 characters with the SQL fold took 1.3 s on the machine it was written on, because `substr` walks the text from its start each time. A `sqlite3` write of a long text pays the same cost in its trigger, and so does an Omanotes edit that changes only case or accents: with a 60 000-character body that edit took about 2.7 s against 20 ms for an edit that changes the text. Notes are short, so this was accepted rather than adding a marker column to tell the two writes apart.

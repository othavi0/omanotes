# Read and write the database through one Store and the omanotes-db binary

Omanotes used to run the `sqlite3` CLI once per read and once per write (ADR-0001), with SQL built as text in `data/Db.js` (ADR-0002). Every bar widget had its own `Db`, so a reload of a shell with three monitors and the service started 17 processes, and the start-up 21. Each `Db` kept its own copy of the items and the history. A write carried the title and the body in argv, twice counting the search copy, and an argument over 128 KiB kept the process from starting without a word: a body of about 65 000 ASCII characters or more was lost (issue #55). Two start-ups raced to migrate, and a TEMP table and the words on stderr told the loser to read the version again.

The data layer now talks to `bin/omanotes-db.<machine>`, a C# NativeAOT binary built from `db/` that lives for one request. It uses the system's `libsqlite3.so.0`, holds every statement and migration, and has no clock and reads no environment variable. One request is one spawn:

- argv is `[bin, protocol, "run", dbPath]`. No user text travels in argv.
- stdin is one JSON object of up to 1 MiB: the writes in order, each `{ id, by, op, at, args }`, and a `sync` that asks for the snapshot after them. The binary gives up with `timeout` when stdin stays open 30 s without a byte.
- stdout is two lines in protocol 1. Line 1 is `{"results":[...]}`, the result of each write, written as soon as the writes are done. Line 2 is the snapshot, when the request asked for one, written as it is read. Protocol 2 changed this: one line per write, each written as soon as its write ends, then the snapshot (ADR-0020). Protocol 1 still gets the two lines.
- This bullet describes protocol 1; ADR-0020 gives the exits of protocol 2. Exit 0: both lines are whole. Exit 3: line 1 is whole and the snapshot failed; the last line of stderr is `{"syncErr":{"err","detail"}}`. Exit 1, 64 or 70: there is no line 1, and the last line of stderr is `{"err","detail"}`. Any other exit or a signal is a crash. `Db.reply` keeps the results of line 1 whenever that line is whole, even when the process died after it. That held only for a process that died after line 1: a request killed during a later write lost the results of the writes before it, which were committed, and an add came back to the editor and was saved twice (#57). ADR-0020 replaced line 1 with one line per write, and `Db.reply` keeps each whole one.
- The snapshot is everything a reload reads, in one read transaction: the settings row with the file size, the counts, every item, the newest 500 history entries, the alarms, and the ids each search matched. Each cell comes in the storage class `sqlite3 -json` printed, and an infinite REAL as `9e999`.

`data/Store.qml` is a singleton (`pragma Singleton`, listed in `data/qmldir`), so the three bar widgets and the service share one. It keeps the write queue, the snapshot, the watcher and two lanes (`data/Lane.qml`), one for writes and one for reads, so a write that waits on a lock held outside never holds up the list. A request carries every write queued so far and the sync, so a write and the reload it causes are one spawn. `data/ItemsDb.qml` and `data/AlarmsDb.qml` are views over the Store with the API they had: the filter and search of a panel, the settings overlay, the drop overlay, the alarm overlay and its retry, and the signals. `data/Db.js` keeps what has no SQL: `SETTINGS`, the coercion of raw cells (`parseSettings`, `parseAlarms`, `parseCounts`, `clampedInt`), the overlays, the request with `wellFormed`, `reply`, and `ERROR_TEXT` with `errorText`. `data/DbCore.qml` is gone.

## Considered options

- The CLI as it was. The spawn count grows with the monitors, and the #55 loss is in the transport.
- A resident helper process. It costs 6 to 8 MB per instance for as long as the shell runs, against 0 before, and needs a way to die with the shell.
- C# inside the shell's process. A crash in it takes the whole omarchy-shell down, and a loaded `.so` never unloads.
- One view per monitor with a spawn of its own. It makes M + 1 spawns per reload and M copies of the rows, where the singleton makes one of each.
- Coercion in C#. It repeats the rules of `Number()` and `Math.round` in a second language, and the tests would need the old JS as an oracle for good. The snapshot sends raw cells instead, and the same JS coerces them.
- One lane. Every snapshot would land in the order it was asked for, and the rules that drop an old read would go. A reload would then wait behind a write held by a lock outside, and `test/behavior.sh` requires the list to reload meanwhile. The two lanes stay, with the WAL rule below.
- The snapshot built whole in memory, then written. Its peak grew with the database: 7.5 to 7.8 MB on 1 000 items of 200 characters, 8.8 to 9.0 MB with 1 200. It is written as it is read instead.

## Consequences

- Requests per event, measured with three monitors and the service: start-up 1 (21 before), a write from outside 1 (17), a write through the IPC 2 (18): the write with its snapshot, then the watcher's read, which the binary answers `unchanged`. A type filter costs no spawn, and a search costs one that carries only ids when the file did not move.
- The snapshot carries a stamp, the file change counter of the header, which every commit moves in rollback-journal mode. The binary reads the header through SQLite's own file handle (`SQLITE_FCNTL_FILE_POINTER`). Opening the file a second time and closing that descriptor drops every POSIX lock the process holds on it, the SHARED lock of the read included: 40 of 40 snapshots read that way beside a writer failed as `corrupt`. `db/BannedSymbols.txt` bans the calls that open a second descriptor.
- A request always sends the stamp it shows as `since`, and the binary answers `unchanged` when the file did not move, so the echo of a write rebuilds nothing (ADR-0004). The ids each search matched come in every answer, `unchanged` included. A view emits `itemsUpdated` only when the rows it shows changed (`Db.sameRows`), so an echo never cancels a drag.
- In WAL the stamp is -1 and no read is skipped. The views never go back in time: a read that ran before a snapshot already shown and reads an older stamp is dropped, and in WAL, where the stamp cannot order them, a read sent before a write whose result has landed since is dropped. That read may have run after a change made outside that the write's snapshot does not hold, so the Store asks for another read, which carries the write and is shown (#57). A request sent after the snapshot shown was applied is shown whatever its stamp, since a file replaced by hand, such as a restored backup, starts its counter again.
- A view drops what it laid over the rows for a write once `Store.covered`, the id of the last write a shown snapshot includes, reaches that write. For a read, that is the last write whose result had landed when the read was sent. The settings, the alarms and a drop in the list all follow that rule, so a read that ran before a write ended never drops the write's overlay (ADR-0014, ADR-0015, ADR-0016).
- A view says whose it is once, `Store.attach("widget")` or `Store.attach("service")`, and every write it queues goes out as that side. The binary checks each write against its op: `alarm.*` only from the service and `settings.set` only from a widget. No caller of `Store.write` can name another side, so ADR-0015 and ADR-0016 hold in the binary. Another QML file of the plugin could still attach as the service: the check stops a mistake, not code that sets out to break it.
- Each write is its own transaction, and one that fails is its own result. An exception that is not an `OpException` is that write's `internal`, and the writes after it still run. After the first `busy` of a request, the writes after it answer `busy` at once: a lock held outside would make each wait 5 s more.
- An alarm write names the 11 columns of protocol 1, no more and no fewer. A column the file has beyond them, from a later schema or the user, keeps its DEFAULT on insert and its value on save.
- A search goes out cut to `Db.MAX_QUERY` (200) units, so its LIKE pattern stays far under the 50 000 bytes SQLite takes. A search SQLite still refuses fails its own view with `{"err","detail"}` in place of the ids, and the rest of the snapshot goes out.
- The wire carries codes. The words stay in `data/Db.js`: "item not found" and "database is locked" as before, and SQLite's own words for `io`, `refused`, `corrupt` and `sqlite`. A snapshot over 64 MiB, counted in bytes written, is `response_too_large`, with its own words. The Store adds `crash` and `no_binary`.
- `wellFormed` turns a lone surrogate into U+FFFD before the request is written, as the CLI's argv did. The QML engine would send it raw, and the binary refuses an escaped one. Each write is serialized once when it is queued (`Db.writeJson`) and measured unit by unit (`Db.utf8Length`).
- The Store reads the machine from `/proc/sys/kernel/arch`, which the kernel documents as the output of `uname -m`, and costs no spawn. A machine with no binary, or a kernel without that file, gets `no_binary` with the path it tried. The kernel version that added the file was not checked.
- A start that fails (a missing file, no exec bit) emits no `exited`. The Lane reports it as `no_binary`, the writes in it fail in their panel, and the queue moves on. A failed read or request asks again from 500 ms up to every 30 s. A snapshot over 64 MiB is the exception: the binary finds it only after writing 64 MiB, which the shell collects, so a retry would cost that again each time. The Store tells it once, does not ask again and stops a retry already armed (`Db.retriesRead`). Until a snapshot lands, the next change of the file reads again, before the first snapshot too, so a file that shrinks shows its rows and the service's alarms with no panel opened. A write and a view that attaches also read (#57). A spawn that runs past 30 s, and 5 s more for each write it carries, is killed and answers as a crash, with the result lines it wrote (ADR-0020).
- The Lane writes the request in `onStarted`, closes stdin, and starts the binary with an empty environment: a `DOTNET_*` variable of the session changes the runtime's memory limits. Each spawn gets collectors of its own, destroyed once its answer is read, so no text of a snapshot outlives the spawn. The binary's lines on stderr, such as a migration it ran, go to the journal.
- The watcher `FileView` has `preload: false`. Preloaded, every copy of it held the whole database file in memory. It is reloaded once, when the first snapshot lands, because a watch set while the folder did not exist watches nothing.
- While no view is attached, the Store holds no rows, reads nothing and watches nothing. The writes already queued still go out, without a sync, since each was accepted; one that fails goes to the journal. Like every component of the plugin, the Store keeps its code across a plugin reload until the shell restarts (ADR-0017). The first view that attaches after a time with none makes it read the file again.
- An alarm write refused for what it is (`bad_request`, `forbidden`, `too_large`, `refused`) stays laid over its row and is not retried: it would be refused again. The CLI version retried a refused one forever.
- A request is at most 1 MiB. `Store.write` refuses at once a write over `Db.MAX_WRITE_BYTES`, the cap less 16 KiB kept for the sync, with "text too large to save", and the editor gets the text back. The Store sends what fits of the rest. A body of 70 000 characters, lost before, is saved.
- Protocol: argv[1] is `PROTOCOL` from `data/Db.js`, and the binary answers every protocol from its `Min` to its `Current` (`db/Wire.cs`). A release that raises `Current` keeps `Min = Current - 1`, because the old QML runs against the new binary between an update and the restart (ADR-0017). Outside that range the toast says "Omanotes was updated. Run omarchy restart shell to finish". The two lines on stdout, exit 3 and the fixed alarm columns changed the wire after protocol 1 was named, and `Current` stayed 1: no release had shipped the binary yet, and `main` only had it inert. Protocol 1 has shipped since, so protocol 2, one result line per write, raised `Current` to 2 and keeps `Min` at 1 (ADR-0020).
- An update runs the binary it would merge before the merge, which is what `selftest` is for (ADR-0017). The binary is a regular executable file, its ELF `e_machine` names the machine `uname -m` reports, and `selftest` exits 0 under `env -i` with the `PROTOCOL` of the new `data/Db.js`. Otherwise the update is `invalid`, and the plugin folder is not touched. The first update that brings the binary runs the `update.sh` already installed, which has no smoke, so that one update is not checked.
- The notes are the user's alone, in a folder other users can list. Before SQLite opens the database, the binary creates it empty at 0600 when it is missing, and takes the bits of group and others off a file that has them; a file of another owner keeps its mode, since chmod is the owner's. SQLite gives the -journal, -wal and -shm the mode of the database, and a backup's `.tmp` is created empty at 0600 before `VACUUM INTO` fills it (`db/OwnerOnly.cs`). Backups of earlier days keep the mode they had.
- `bin/` is committed, and only `tools/build.sh` writes it. A change to `db/` needs a rebuild and the new binaries in the same commit, or `npm test` fails in `tools/verify-bin.sh --check`. The source hash counts the files git tracks, so a stray file in `db/` changes nothing.
- CI checks that `bin/` is what the source makes too: `.github/workflows/verify-bin.yml` runs `tools/verify-bin.sh --rebuild` on the toolchain of `bin/BUILD.json`, from the Arch Linux Archive day that holds it, the .NET SDK tarball checked by its sha512, and the sysroot packages of a pre-release of the repo.
- Memory of one spawn, measured on x86_64 (`test/bin-rss.test.mjs`). The binary's own memory (RssAnon) is 2.0 MB for a reload of 1 000 items of 200 characters and the same for 2 000, and 2.4 MB for the first spawn on a missing file, which migrates it. The peak of the whole process (VmHWM), which also counts the pages of libc, libsqlite3 and libm, is 7.3 to 7.5 MB for either reload and 7.9 to 8.1 MB for the first spawn. A write of a body near 1 MiB with its snapshot reaches 15.8 MB of RssAnon and 21.5 MB of VmHWM: the request, the text and its search copy each live as UTF-16 and UTF-8 for a moment, and SQLite copies both.
- Known limit: the read transaction stays open while the snapshot is written, so a shell slow to drain stdout holds the SHARED lock that long. A writer waits up to 5 s for it, then answers `busy`.
- Known limit: on a file over 64 MiB, each event still costs the shell 64 MiB: a write with its snapshot, the watcher's read after it, and a panel that opens. That lasts until the binary measures the snapshot before it writes the first byte (#57).

## Gates

Each gate is a test that failed with its defect planted and passes without it.

- One Store for three widgets and the service (`test/startup.sh`). It failed when the service imported `data/` through a second path.
- One request per reload, whatever the number of monitors: a write from outside, and every panel asking at once (`test/startup.sh`). It failed when `Store.reload` stopped batching the calls of one tick.
- No `omanotes-db` process alive after the requests, and none after a spawn killed past its limit (`test/startup.sh`). It failed when the Lane closed stdin 1.5 s late, and with no limit.
- A snapshot is one read transaction: 40 snapshots beside a writer outside that commits two items together, none torn and none `corrupt` (`test/bin-concurrency.test.mjs`). It failed 40 of 40 with the header read through a second descriptor.
- The binary's own memory, RssAnon, stays at 3 MB or less for a reload of 1 000 or 2 000 items and for the first spawn on a missing file, and grows by 128 kB or less from 1 000 to 2 000 items; the peak, VmHWM, is reported and not gated, because the shared library pages in it moved from -276 to +356 kB between runs; a write near 1 MiB stays at 16 MB of RssAnon or less (`test/bin-rss.test.mjs`). It failed when the snapshot was built whole before it was written: RssAnon grew 344 kB with 1 000 more items.
- A body of 70 000 characters is saved (#55), and one over the cap is refused at once and given back (`test/startup.sh`). It failed with a cap of 64 KiB.
- A start that fails shows its error in the panel and the queue moves on (`test/startup.sh`). It failed when the Lane ignored a start that failed.
- With the service and the widgets gone, as in a plugin reload, a write queued as they went still lands, the Store holds no rows and spawns no read, and the views that come back show what changed meanwhile, through the same Store (`test/startup.sh`). It failed when the Store read again only before its first snapshot, and when writes waited for a view.
- A read held from before a write lands after that write's snapshot and is dropped, in rollback-journal mode and in WAL (`test/startup.sh`). It failed without the stamp rule, and in WAL before the rule on `covers`. In WAL, a read held before it runs, past a write's snapshot and a change made outside, is dropped and read again, so the change shows before the watcher's 30 s (`test/startup.sh`). It failed when the rule dropped the read and asked for nothing.
- A snapshot over 64 MiB is read once and not retried (`test/startup.sh`, with the stub's `too-large`). It failed when the Store retried it: three requests in 3 s. A shell that starts on such a file shows the rows and the service's alarms on the next change of the file, with no panel opened (`test/startup.sh`). It failed when the watcher read only once `ready` was true.
- An update whose binary is missing, a symlink, not executable, built for the other machine, failing its selftest, or refusing the protocol of its own `data/Db.js` ends `invalid` and writes nothing in the plugin folder, with or without `omarchy-plugin-validate` (`test/update.sh`). Each check failed with the smoke removed. The check for the other machine's build also failed with only the ELF check removed, when qemu's binfmt started the aarch64 binary.
- A database the binary creates is 0600, one left 0644 is 0600 after a read, the -wal and -shm of a WAL database it read are 0600, and so is a backup (`test/bin-mode.test.mjs`). All four failed against the binary of 16b93ed, which left each file 0644.
- The aarch64 binary passes its selftest under qemu. With `OMANOTES_REQUIRE_ARM=1` a missing qemu or sysroot fails the test instead of skipping it (`test/bin-protocol.test.mjs`).

## Tests

- The QML scripts replace the binary with `test/lib/stub-db.sh`, which logs each request in `db.log` with the ops it carries and holds or fails the requests a script names. `sqlite3` stays as the oracle and as someone editing the file by hand.
- A guard, not a gate: in `too-large`, a write lands and hears its own result, and its failed snapshot is not asked again (`test/startup.sh`). It holds the stub to the binary: it failed when the stub dropped the write's result line, which the Store then took as a crash and retried.
- `test/lib/v0.sql` is the frozen schema of a database from before versioning. The scripts write their rows on it, and the binary migrates the file when it opens it.
- `test/fixtures/parity/` holds what the SQL of before the binary left and read, run once and frozen: the tables after each write, the search matches, the schema and the cells the old reads printed. The parity tests (`test/bin-parity.test.mjs`, `test/bin-cells.test.mjs`, `test/bin-schema.test.mjs`) hold the binary to it. A new write has no old SQL to match; its tests state what it must do. `node test/lib/freeze-parity.mjs` made the fixtures at commit 4ead611, with sqlite3 3.53.4; that commit is the last one where the generator runs. A new step in `Steps` leaves them as they are: the tests compare each live row only in the columns of its frozen row, and only the `sqlite_master` entries the fixture holds, so a new column, table or index is left to its own tests. A step that changes an old column or an old entry fails them, and the frozen value is edited by hand in the same commit (`test/fixtures/parity/README.md`).

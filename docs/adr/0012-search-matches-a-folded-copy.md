# Search matches a folded copy of title and body

SQLite's `LIKE` and `lower()` only fold ASCII, so a search for `CAFÉ` missed `Café`, and the sqlite3 CLI has no ICU to fold the rest. Each item keeps a folded copy of its title and body in `search_title` and `search_body`, and `listSql` folds the query the same way before matching the copy with `LIKE`. `searchText` in `data/Db.js` folds: lower case, then the accents of the Combining Diacritical Marks block (U+0300 to U+036F) dropped through NFD, one UTF-16 unit at a time. `addSql` and `updateSql` write the copy with the item.

## Consequences

- The copy that `addSql` and `updateSql` write is text built in JS and quoted by `q()`, like every other value (ADR-0002).
- Items inserted or edited with `sqlite3`, outside Omanotes, do not write the copy. Two triggers fold it in SQL for them: `items_search_insert` when an insert leaves `search_title` NULL, and `items_search_update` when an update sets the title or body and leaves both copies as they were. A write that sets a copy itself is kept as it is. An Omanotes edit that keeps both copies the same, such as a change of case only, is folded again by the trigger, with the same result.
- The SQL fold goes through the table `search_map`, which holds every character `searchChar` changes (2299 rows), one character at a time. The migration that adds the columns (`searchCopyMigration`) creates the map and the triggers, and folds the items already there. Folding one unit at a time is what lets the SQL match the JS on every item; folding whole strings can differ, as Node's `toLowerCase` does on a final Greek sigma.
- Characters outside the Basic Multilingual Plane are not folded, in JS or in SQL.
- Building `search_map` takes about 45 ms in Quickshell, so the entry is a function and runs only for a database below it (ADR-0011). Filling 1000 items of 1000 characters took 1.3 s on the machine it was written on, because `substr` walks the text from its start each time. A `sqlite3` write of a long text pays the same cost in its trigger, and so does an Omanotes edit that changes only case or accents: with a 60 000-character body that edit took about 2.7 s against 20 ms for an edit that changes the text. Notes are short, so this was accepted rather than adding a marker column to tell the two writes apart.
- The map comes from the JS engine's Unicode tables and is stored in the database when it migrates. The Quickshell and Node builds used when this was written give the same map. A later Unicode change to a character can leave the map and the copies from before it folded the old way.

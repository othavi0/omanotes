# Watch the database file to pick up changes

The database has several writers: the plugin, through the one Store of the shell (ADR-0018), and anyone running `sqlite3` by hand. There is no channel between them, so the Store watches the database file with a `FileView`. A change to the file restarts an 80 ms timer, and the Store asks for a snapshot when it fires (`data/Store.qml`). The file on disk is the single source of truth.

## Consequences

- This depends on the rollback journal (`journal_mode=delete`, the SQLite default and the mode of the live database). In WAL mode, writes land in `scratchpad.db-wal` and the main file only changes at checkpoint, so the watcher would miss them. Switching to WAL means replacing the watcher. The binary never changes the journal mode.
- The watcher has `preload: false`: it needs the path, not the bytes. Preloaded, each watcher kept the whole file in memory. The Store reloads the watcher once, when its first snapshot lands, because a watch set while the folder did not exist watches nothing.
- A write of the plugin carries its own reload: the request asks for the snapshot after its writes. The watcher then fires on that same write, and the read it asks for sends the stamp of the snapshot shown as `since`. The stamp is the file change counter, which every commit moves in rollback-journal mode, so the binary answers `unchanged` and no list is rebuilt. A view emits `itemsUpdated` only when its rows changed, so that echo also leaves a drag in progress alone. In WAL the stamp is -1 and no read is skipped.
- A reload is one read of everything, in one read transaction: the settings row (ADR-0016), the counts, every item, the history, the alarms and the ids each search matched. With any number of monitors it is one spawn. A reload asked for while a read runs drops that read's answer and runs again when it ends, so after a burst of writes every view shows the last one. `test/panel.sh` writes with `sqlite3` from outside, holds the read open across a second write, and checks that the panel catches up through the watcher alone.
- The panel's filter and search narrow `items`. The IPC reads `allItems`, which every snapshot carries unfiltered, so the panel cannot hide an item from a script. A filter by type is answered from the rows the view has, with no spawn.
- The alarm service's view, `data/AlarmsDb.qml`, reads the alarms of the same snapshot (ADR-0015). It keeps each write it made in memory over the rows until a snapshot read after the write ended lands. That is an exception to the file being the single source of truth, limited to rows the service wrote itself.
- The IPC writes inside `db.fromScript`, so a script's write reloads the panel but emits none of the signals the panel answers as its user's action (a selection change, a toast). Adding, toggling and clearing history from a script do not move the selection or commit an edit the user has not left (ADR-0007). Removing the item open in the editor moves the selection, because the reload drops the selected row, but commits nothing: the editor throws its text away and shows "Item removed elsewhere" (`onItemsSynced` in `ui/ItemsTab.qml`). The text of a failed edit still waiting to come back to the editor goes the same way when its item is removed (`restoreFailed`). A filtered list cannot tell a removed item from a hidden one, so the panel checks `allItems` too. One snapshot carries both, so that check never sees rows from before the removal.

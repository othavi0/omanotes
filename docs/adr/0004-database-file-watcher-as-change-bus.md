# Watch the database file to pick up changes

The database has several writers: the `Db` of each bar widget (one per monitor, which also serves the IPC and is shared with that widget's panel) and anyone running `sqlite3` by hand. There is no channel between them, so each `Db` watches the database file with a `FileView`. A change to the file and the end of one of its own writes restart the same 80 ms timer, and the `Db` reloads when it fires (`data/DbCore.qml`). The file on disk is the single source of truth.

## Consequences

- This depends on the rollback journal (`journal_mode=delete`, the SQLite default and the mode of the live database). In WAL mode, writes land in `scratchpad.db-wal` and the main file only changes at checkpoint, so the watcher would miss them. Switching to WAL means replacing the watcher.
- One write reloads each `Db` once, including the one that wrote it. With several monitors, that is one reload per monitor.
- A reload runs four reads, each in its own `Process`: counts, the filtered list, every item and history. A reload that arrives while one of them runs marks it stale, and that read runs again when it ends, even if it failed. The list re-runs with the latest filter and search. After a burst of writes, every read shows the last one. `test/panel.sh` writes with `sqlite3` from outside the `Db`, holds the reads open across a second write, and checks that the panel catches up through the watcher alone.
- The panel's filter and search narrow `items`. The IPC reads `allItems`, which a reload always fetches unfiltered, so the panel cannot hide an item from a script.
- The alarm service runs one more `Db`, `data/AlarmsDb.qml`, that reads only the `alarms` table (ADR-0015). It shares the watcher, the queue and start-up with the widgets' `data/ItemsDb.qml` through `data/DbCore.qml`, and neither carries the other's reads or writes. One write reloads it once too, and an alarm write reloads every widget's `Db`, four item reads per monitor. The alarm store keeps each write it made in memory over the rows until a read that started after the write ended lands. That is an exception to the file being the single source of truth, limited to rows the service wrote itself.
- The IPC writes inside `db.fromScript`, so a script's write reloads the panel but emits none of the signals the panel answers as its user's action (a selection change, a toast). Adding, toggling and clearing history from a script do not move the selection or commit an edit the user has not left (ADR-0007). Removing the item open in the editor moves the selection, because the reload drops the selected row, but commits nothing: the editor throws its text away and shows "Item removed elsewhere" (`onItemsSynced` in `ui/ItemsTab.qml`). The text of a failed edit still waiting to come back to the editor goes the same way when its item is removed (`restoreFailed`). A filtered list cannot tell a removed item from a hidden one, so the panel checks `allItems` too. `Db` emits `itemsUpdated` only after the `allItems` read of the same reload lands, so that check never sees rows from before the removal.
